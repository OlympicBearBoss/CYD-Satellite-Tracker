# Процесс сборки и выпуска прошивки

## Источник версии

Единственный источник версии для обычных CI-сборок — файл `firmware/VERSION`.
Для релизной сборки по тегу версия берётся из тега `firmware-v...`.

## Перед сборкой

1. Проверить, что изменения основаны на актуальном `main`, а не на случайной старой ветке.
2. Сравнить `firmware/src/main.cpp`, UI-экраны, языковые строки, Wi-Fi, touch, спутниковую телеметрию и сенсорные модули с предыдущей принятой версией.
3. Проверить, что известные рабочие функции не исчезли.
4. Обновить `firmware/VERSION`.
5. Создать `docs/releases/<VERSION>.md` с фактическим списком изменений и ограничений.
6. Запустить GitHub Actions и проверить полный результат.

## Артефакты

Каждый CI-комплект должен содержать:
- full-flash BIN;
- отдельные bootloader / partitions / boot_app0 / application BIN;
- ELF для диагностики;
- motor-test BIN отдельно от основной прошивки;
- инструкцию по прошивке;
- changelog конкретной версии;
- build-info с commit SHA, датой и URL CI;
- SHA256SUMS для проверки целостности.

Motor-test — отдельная диагностическая прошивка. Её нельзя путать с основной.

## Постоянное хранение

Actions artifacts удобны для проверки, но имеют срок хранения. Для постоянного хранения выпуска создаётся GitHub Release по тегу:

`firmware-v2026.11.18.97`

Workflow прикрепляет к Release все файлы из каталога `release/`. После публикации нельзя заменять бинарные файлы под тем же тегом: любое исправление получает новый номер.

## Статусы

- **CI success** — компиляция и упаковка прошли.
- **Artifact verified** — ZIP и ожидаемые файлы доступны, контрольные суммы рассчитаны.
- **Hardware tested** — прошивка установлена и проверена на реальной плате.
- **Stable** — все необходимые проверки пройдены; только тогда версия рекомендуется для обычного использования.

Успешная компиляция сама по себе не означает аппаратную проверку или стабильность.
